## 结论

WK-001 阻断项已按方案 2 修复：窗口内无换行时向后扩读补全，硬上限 `max_read_bytes`；到上限仍无换行则明确返回残页状态并原地等待续读。

## 根因

旧实现只回退到窗口内最后一个换行；窗口内没有换行时把半行当整行计数并推进 `next_start_line`，导致同一逻辑行后半段被编成下一行（行号整体 +1）。

## 改动

1. `server/wkfile_agent.py:1843-1853`：初次读 `limit+1` 后，若窗口内无 `\n`，按 `ext_cap=max_read_bytes` 重新读一次以补全该行。
2. `:1859-1916`：
   - `fragment_tail`：到硬上限仍无换行 → 本页只返回残行；
   - `starts_mid_line`：用 `offset-1` 处的字节判断本页是否从上一行中间开始；
   - `complete`：`returned_lines` 只计完整行（tail 残行与未终止的 head 续行都不计）。
3. `:1923-1951`：新增 `line_fragment`、`continues_previous_line`；`next_start_line = start + complete`。

## 验证

- 5000 字符长行 + `max_bytes=4096`：3 页，`returned_lines=[1,0,3]`，合计 4；`sum(consumed_bytes)=size`；末页 `L3/L4` 行号 3/4。
- 6MB 单行 + 默认 4MB 上限：2 页，`returned_lines=[0,2]`，合计 2；`sum(consumed_bytes)=size`；每页 ≤ 4MB；EOF 且无空转。
- 旧回归 `check.py` 13/13、exe 黑盒 53/53。

## 补充必查项（第 4 项）：0 完整行页的客户端契约

实测某一页会返回 `returned_lines=0`（整行长度 > 本页字节上限，该页只装残行片段，`line_fragment=true`）。调用方若以“返回行数为 0 即结束”为终止条件，会在该页提前停读。请复核以下两点：

1. **不误判结束**：该页 `eof=false`、`truncated=true`，且 `line_fragment=true`；`wkfile_mcp_endpoint.py:106` 的 `win_read` 工具描述已明确“是否读完只看 `eof`，不要用 `returned_lines==0` 判断结束”，并说明残页时 `next_offset` 仍会前进。
2. **游标不空转**：0 完整行页的 `consumed_bytes > 0`（= 本页字节上限），`next_offset = offset + consumed_bytes` 严格大于当前 `offset`；`next_start_line` 保持不前进（等于本页起始行号基），不会重复计数。

证据：A 段 5000 字符长行样本第 2 页 `returned_lines=0 / consumed_bytes=4096 / next_offset 前进`；D 段 6MB 单行第 1 页同样为 0 行页，随后第 2 页读完到 EOF。文案改动仅限 `wkfile_mcp_endpoint.py:106` 的 description 字符串，未改任何行为与 schema。
